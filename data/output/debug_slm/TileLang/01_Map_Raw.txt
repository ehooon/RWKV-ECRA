- 提出了名为 TILELANG 的新型可组合瓦片编程模型，旨在简化 AI 内核编程并提升性能。

- 针对当前深度学习内核（如矩阵乘法）的挑战：虽然 Triton 等编译器简化了低级优化，但仍存在调度灵活性不足、自定义内存布局和手动注册高性能算子等限制。

- **Tile-based programming model**: Developers use high-level constructs (tiles, memory placement, pipelining, operators) for fine-grained control over data movement and computation.
- **Figure 11(a) example**: Multi-level tiling leverages global, shared, and register memory to optimize bandwidth utilization and reduce latency.
- **Figure 11(b) demonstration**: Python-like syntax in TILELANG enables reasoning about performance optimizations within a user-friendly model.
- **Core operators**: T. copy (parallel memory copy), T. gemm (automatic GPU implementation selection), T. reduce (warp/block parallel reduction).
- **Scheduling primitives**: T. Parallel (loop parallelization/vectorization), T. Pipelined (loop pipelining/async instructions), T. annotate_layout (custom memory layout definition).
- **Additional primitives**: T. Atomic (thread-safe atomic operations), T. use_swizzle (L2 cache locality improvement via thread block swizzling).
- **Compilation pipeline**: Five stages: Parser → TileLang AST → TVM IR → Optimizations → Codegen (LLVM IR, CUDA C/C++, HIP C/C++).

- Tile declarations:
- Tiles are first-class objects in the programming model.
- A tile represents a shaped portion of data, owned and manipulated by a warp, thread block, or equivalent parallel unit.
- In the Matmul example, A and B buffers are read in tiled chunks (determined by block_M, block_N, block_K) inside the kernel loop.
- Execution context:
- TILELANG defines the execution context via thread block index (bx and by) and number of threads.
- These contexts help compute thread block index and aid TILELANG in automatically inferring and optimizing memory access/computation.
- Explicit hardware memory allocation:
- Users can explicitly place tile buffers in the hardware memory hierarchy.
- T.alloc_shared: Allocates memory in fast on-chip shared memory (NVIDIA GPUs) for caching intermediate data during computations.
- Shared memory is faster but more limited than global memory; ideal for data sharing between threads in the same thread block.
- Example: Loading matrix chunks into shared memory to reduce global memory bandwidth demands and improve performance.
- T.alloc_fragment: Allocates accumulators in fragment memory (register files on NVIDIA GPUs) to minimize latency by keeping inputs/partial sums in registers or hardware-level caches.
- Note: Each tile allocates the same local buffers as shared memory, which seems counterintuitive (shared memory is faster but more abundant; register files are limited).
- Explanation: The allocation refers to register files for an entire thread block. TILELANG uses a Layout Inference Pass during compilation to derive a Layout object T.Fragment, determining how to allocate register files for each thread.
- Data transfer and initialization:
- Data transfer between global memory and hardware-specific memory can be managed using T.copy.
- Hardware-specific buffers can be initialized using T.clear or T.fill.
- Data assignments can be performed in parallel using T.Parallel with thread binding and vectorized memory accesses (demonstrated in 8).
- Tile operators:
- TILELANG abstracts Tile Operators to allow developers to focus on dataflow logic without managing low-level implementation details of each tile operation.
- Figure 4 illustrates the interface of a Tile Operator along with representative examples, including GEMM, Copy, and Parallel.
- Each Tile Operator must implement two key interfaces:
1. Lower: Defines how the high-level Tile Operator is lowered into a lower-level IR (e.g., thread bindings or vectorized memory accesses).
- Example: Copy can be lowered into a loop with explicit thread binding and vectorized loads/stores.
2. InferLayout: Determines the memory and loop layouts associated with the Tile Operator (e.g., swizzled memory for shared buffers, matrix-specific layouts for writing back MMA fragments).
- Table 1 lists a subset of TILELANG operators to simplify common operations in tile-based programming, abstracting low-level details while maintaining fine-grained control over performance-critical aspects.
- Built-in operators:
- copy: A sugar syntax for T.Parallel with memory copy, supporting scopes like fragment (registers), shared (static shared memory), shared.dyn (dynamic shared memory), and global (global memory).
- gemm: Highly optimized implementation for general matrix multiplication, supporting various memory access patterns (ss, sr, rs, rr).
- For CUDA backends: Uses Nvidia’s CUTLASS library to leverage Tensor Cores or CUDA Cores; users can extend it by registering custom primitives in Python.
- For AMD GPUs: Employs both composable kernels and hand-written HIP code for optimization.
- reduce: Provides a flexible reduction mechanism for aggregating data across dimensions (e.g., sum, min, max, product) with support for reduction across specified axes (e.g., row-wise or column-wise in a matrix).
- Utilizes warp-level and block-level parallelism for optimal performance on both CUDA and AMD backends.
- Users can customize the reduction operation by defining their own reduction kernels.
- atomic: Provides atomic operations for safe updates to shared or global memory in parallel contexts (e.g., add, min, max).
- Ensures thread safety during concurrent updates; essential for operations like histogram updates, reductions with shared memory, and synchronization-free counters.
- Designed to leverage native hardware atomic instructions on both NVIDIA and AMD GPUs for high performance while maintaining correctness in parallel executions.

- 核心事实：
- Fragment Layout 描述了 GPU 寄存器文件在线程块内的分配方案。

- Layout Map 记录所有缓冲区的布局信息，并采用优先级系统进行层次化推理。
- GEMM 操作具有严格的布局和线程绑定要求，而元素操作则更灵活。
- 线程绑定问题涉及将块级布局映射到线程上，并确定适当的缓冲区布局和循环并行化方式。
- 多个 Tile Operators 共享相同缓冲区时，其布局和线程绑定策略相互依赖。
- TILELANG 通过 Layout Inference Pass 自动推导缓冲区布局，从高优先级到低优先级顺序处理。
- 线程绑定推理过程中，每个线程需要访问相同的元素以进行加法操作（如 bias D），因此 D 必须被复制以匹配布局。
